# 投稿证据矩阵

本文档把论文中的每个核心 claim 映射到当前证据、日志位置、可写结论和剩余风险。它的目的不是重复技术报告，而是帮助审稿人-作者迭代时快速判断某句话能不能写进主文。

可用下面的自检脚本检查本机 artifact 是否仍然存在：

```bash
python3 tools/benchmarks/run_submission_gate.py
```

这个统一 gate 会执行 Python helper 语法检查、关键 benchmark shell 入口语法检查、论文/报告/入口文档危险表述检查，以及 artifact audit。若只想检查 artifact，可以单独运行：

```bash
python3 tools/benchmarks/audit_paper_artifacts.py \
  --csv /tmp/paper_artifact_audit.csv \
  --md /tmp/paper_artifact_audit.md \
  --fail-required
```

artifact audit 先检查“证据链文件是否存在”，并已对部分核心 claim 加入数值级校验：x100 cross-edge strong-baseline fairness 的各 baseline cross time 和 speedup；x200 partial double-buffer routing 的 cross time、kernel time、search recall 和结构 edge count；source-centric checked negative ablation 的 SIFT30 cross/kernel/writeback；universal flat double-buffer route 的 SIFT30 skip-additional cross-edge、Amazon 1% x200 full-quality cross/recall 和 Amazon 1% x100 full-quality boundary；mixed exact/GNN router 的 L1000 表项；packed exact-anchor x200/x400 的 L1000/L5000 recall；x200 packed exact direct-H2D A/B 的 pack/kernel/fill/group time；x200 warp-kernel/fill-thread negative ablation 的 group/kernel/fill/recall；Graph output-boundary reserve A/B 的 10%x40 reserve on/off 和 x200 auto-reserve 数值；Graph output-boundary NeighborList small-buffer A/B 的源码状态、x200/10%x40 fill/reserve 数值和 48-inline 负例；10%x40 bounded-complete fallback 的 build/物化开销和 bounded search recall；10%x40 宽 Lsearch sweep 的 CPU/FastGrnnd recall；x400 reverse-tail A/B 的 build、recall 和结构指标；x400 compact-D2H 负/不稳定 ablation；x100 additional_edges/output-boundary smoke 的 `total/gen/add/kernel` 分项。`PENDING_EXPERIMENT` 和 `MISSING_EXPERIMENT` 对应投稿前仍需补的实验。`check_paper_claim_language.py` 默认自动扫描 reviewer-facing Markdown 文档（根 README、`docs/`、`scripts/benchmarks/`，排除 `docs/archive`），防止出现未加限制的“无损替代”“x400 已解决”“自研 kernel 普遍超过 cuBLAS/cuVS”等危险表述。它不替代人工审稿，但能阻止最常见的 overclaim。

如果已经跑完 x400 repair/reverse-tail A/B，可以把输出目录传给自检脚本：

```bash
python3 tools/benchmarks/audit_paper_artifacts.py \
  --x400-root /path/to/x400_ab_root \
  --fail-submission
```

如果已经跑完 mixed exact/GNN router A/B，先汇总，再把输出目录传给自检脚本：

```bash
python3 tools/benchmarks/summarize_group_graph_router_ab.py /path/to/router_ab_root \
  --csv /path/to/router_ab_root/router_ab_summary.csv \
  --md /path/to/router_ab_root/router_ab_summary.md

python3 tools/benchmarks/audit_paper_artifacts.py \
  --router-root /path/to/router_ab_root \
  --fail-required
```

`DRY_RUN=1` 产生的 `NA` 行不会被 audit 判为已完成实验；router A/B 必须包含实测 `index_ms` 和 `avg_recall`。

`--fail-required` 只保护当前已经写进主 claim 的 artifact；`--fail-submission` 会把所有 pending/missing 项都当成失败，用于最终投稿前 gating。

## 2. 不能作为主结论的结果

| 结果 | 为什么不能作为主结论 | 可以怎么使用 |
|---|---|---|

## 4. 推荐主文写法

可以写：

> Our results show that UNG construction is best treated as an irregular group workload rather than a single dense linear algebra problem. Grouped fused topK provides robust speedups for cross-edge construction, while intra-group graph construction requires workload-aware routing and quality-aware pruning.

中文对应：

> 实验表明，UNG 构建应被视为不规则 group workload，而不是单一密集线性代数问题。Grouped fused topK 能稳定加速 cross-edge 构建；组内图则需要按 group size 和质量需求进行路由与剪枝预算控制。

避免写：

- “FastGrnndCuda 无损替代 CPU Vamana。”
- “我们的 GEMM kernel 普遍快于 cuBLAS/cuVS。”
- “skip additional_edges 的时间就是完整系统时间。”
- “x400 已经证明 GPU group graph 普遍可替代 CPU。”
