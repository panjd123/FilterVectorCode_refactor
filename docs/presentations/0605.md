# 0605 展示文档：UNG GPU 构建与查询入口加速

本文整理 UNG 这段时间的 GPU 化工作。目标读者是假设不了解 UNG、Tagore、Vamana 和我们代码细节的 reviewer，因此先解释问题，再解释方法和实验。

为了避免结果混乱，本文把三类结果分开：

| 模块 | 解决的问题 | 当前最重要结果 | 口径 |
|---|---|---|---|
| 组内 PG / group graph | 每个 label group 内部怎么建可导航点图 | Amazon 1%x200 group graph `2.22x`；10%x40 group graph `3.54x` | full-quality 构建 + search recall |
| 跨组边 / cross-edge | 父子/相关 group 之间怎么做大量 irregular topK 连边 | Amazon 1%x100 cross 相对 CPU exact scan `2.82x`，相对 cuVS per-group `4.39x`；10%x40 diagnostic cross `6.48x` | full-quality 和 diagnostic 分开 |
| 查询入口组 / scan | query labels 怎么快速找到覆盖正确的入口 groups | Amazon 100%x40、`nq=10240` 上 `59.83 ms`，相对 CPU scan 128T `19.85x` | 独立 benchmark，尚未接入正式 graph search |

## 0. TLDR：这部分工作到底证明了什么

这部分工作解决的是 UNG 里三个高成本阶段：

```text
index build:
  group graph      -> 每个 label group 内部建点图
  cross-edge       -> 不同 group 之间补连边

query:
  entry group scan -> 从 query labels 找入口 groups
```

组内图不是简单把 CPU Vamana 换成 GPU topK，而是针对不同 group size 选择不同构图路径：

```text
小 group: bounded-complete / CPU fallback
中等 group: packed exact-anchor
大 group: FastGrnndCuda + reverse-tail / repair
```

三个核心结论：

| reviewer 会问的问题 | 简短回答 |
|---|---|
| 为什么精度更高？ | 因为我们不只保留最近邻，还显式补了 anchor/tail/reverse/repair 这类导航边，减少 strict topK 和轻量 NN-Descent 图的局部化、低出度和弱连通问题。这里的“更高”主要是相对 Tagore 原始/naive topK/轻 prune 负例；相对 CPU Vamana 的目标是接近或对齐，而不是宣称所有场景都超过。 |
| 为什么更快？ | 因为我们避免了 Tagore/CPU Vamana 的重 prune，同时把多 group 打包，去掉 host pack、重复 D2H scatter 和 `std::vector` 图物化开销；很多实验里 GPU kernel 不是主瓶颈，外围才是主瓶颈。 |
| 在什么数据集上有效？ | 最有效的是 `nx≈128~512` 的中等 group 和 10%x40 这类 many-group workload；`nx>=1024` 的大 group 需要 reverse-tail/repair 质量路径；`nx<=64` 的小 group 不适合强行上 GPU，应 fallback。 |

当前对外展示应使用的主结果：

| 方向 | 主结果 | 不能夸大的边界 |
|---|---|---|
| group graph | 1%x200 full-quality Index `1.59x`，Group `2.22x`；10%x40 full-quality Index `1.53x`，Group `3.54x` | 不是所有 group 都 GPU 化；小组要 fallback，大组要质量修复 |
| cross-edge | 1%x100 cross 相对 CPU exact scan `2.82x`、相对 cuVS per-group `4.39x`；10%x40 skip-add diagnostic cross `6.48x` | diagnostic 不能混进 full-quality recall 主表 |
| query-entry scan | 100%x40、`nq=10240`，GPU correct-cover `59.83 ms`、`171k QPS`、相对 CPU scan 128T `19.85x` | 这是入口组阶段独立 benchmark；端到端 query speedup 还要接入正式 search path 后复测 |

一句话：

```text
我们的贡献是一个面向 UNG filtered search 的 workload-aware group graph builder，
再加上 cross-edge fused topK 和 query-entry correct-cover scan。
核心不是一个单独的 topK kernel，而是把图质量、GPU/CPU 外围开销和 workload routing 一起处理。
```

## 1. 背景：UNG 里的“组内 PG 建图”是什么

UNG 是一种带过滤条件的向量图索引。每个向量有一组 label，系统先按 label set 把向量划分成很多 group，然后在 group 内和 group 间都建图：

```text
base vectors + labels
  -> label groups
  -> 每个 group 内建一个局部导航图 PG
  -> 再根据 label hierarchy 建 cross-group edges
  -> 查询时先找入口 group，再在图上搜索
```

这里的 **PG / group graph** 指的是：

```text
对同一个 label group 内的点，构造 point-to-point 邻接边。
```

它不是简单的 kNN 表。一个好的 ANN graph 需要满足两件事：

1. **局部精度**：边要连接到相近点，否则距离搜索会绕远。
2. **可导航性**：图不能只在局部小团簇内很密，还需要能从入口点逐步走到正确区域。

CPU Vamana 的质量通常较好，因为它有 alpha / RNG-style prune，会有意识地避免只保留重复的局部近邻。但它在大量 group 或大 group 上构建慢。

## 2. Baseline 和历史负例

### 2.1 CPU Vamana

CPU Vamana 是原始质量 baseline。它不是 exact kNN，而是搜索式构图 + alpha prune。优点是图质量稳定，缺点是慢。

### 2.2 Tagore / 原始 GPU NN-Descent

Tagore 类方法用 GPU NN-Descent 快速产生近邻候选，再做 GPU Vamana-style pruning。它的候选生成快，但原始 prune 在 UNG group 场景里偏重。

### 2.3 Strict topK / naive exact kNN 不是好替代

一个自然想法是：既然 GPU 可以快速算 exact topK，那每个点直接连同组 exact topK 不就可以了吗？

历史实验说明这条路不稳。直接 topK 图容易只保留局部最近邻，缺少跳转边和多样性边，搜索时可能卡在局部区域。

Amazon 1% x200 coverage-query 中，早期 old batched exact kNN 的 UNG 端到端 recall 明显差：

| 方法 | Group ms | Index ms | L1000 recall | L5000 recall | 解释 |
|---|---:|---:|---:|---:|---|
| CPU Vamana group | `8511.72` | `17596.8` | `0.8690` | `0.9080` | 原始质量 baseline |
| old batched exact kNN | `4356.18` | `12595.9` | `0.8159` | `0.8199` | 直接 topK 图，UNG search 质量差 |
| old batched exact + anchor | `5534.10` | `12539.3` | `0.8240` | `0.8290` | 加简单 anchor 仍不足 |

注意：后续结构诊断发现这组 old exact 结果还混入 cross/additional 口径差异，因此不能用它证明“exact 候选一定不行”。但它仍然说明一个重要事实：

```text
不能把“精确 topK 邻居”直接等同于“适合图搜索的可导航图”。
```

## 3. 我们的方法：workload-aware hybrid group graph builder

我们的方法不是单个 kernel，而是一个按 group size 分流的组内图构建器：

```text
for each group:
  if group 很小:
      用 CPU / bounded-complete fallback
  else if group 中等:
      用 packed exact-anchor
  else:
      用 FastGrnndCuda: GNN candidates + reverse-tail / local prune / repair
```

核心思想：

```text
不同 group size 的瓶颈不同，所以不能所有 group 都用同一种 GPU 方法。
```

| group 类型 | 典型问题 | 我们的方法 |
|---|---|---|
| 很小 group | GPU H2D / D2H / fill 开销比计算还大 | CPU fallback 或 bounded-complete |
| 中等 group | exact 计算可承受，质量要稳定 | packed exact-anchor |
| 大 group | exact all-pairs 太贵，需要近似候选 | FastGrnndCuda + reverse-tail / repair |

## 4. 变量和表格字段含义

后面表格会用到这些字段：

| 变量 / 字段 | 含义 |
|---|---|
| `nx` | 一个 group 内的点数，即 group size |
| `Lsearch` | 查询时图搜索候选池大小；越大通常 recall 越高、查询越慢 |
| `L1000 recall` | `Lsearch=1000` 时的端到端 filtered Recall@K，K 通常为 10 |
| `L5000 recall` | `Lsearch=5000` 时的端到端 filtered Recall@K |
| `Group ms` | 组内 PG / group graph 构建耗时，不含全部 cross-edge |
| `Index ms` | 构建阶段总 Index time，不含最终落盘 save |
| `Cross ms` | cross-group edge 构建耗时 |
| `GNN` | GPU NN-Descent 候选生成耗时 |
| `prune` | 从候选池筛出最终出边的剪枝耗时 |
| `H2D / D2H` | Host-to-Device / Device-to-Host 拷贝耗时 |
| `fill` | GPU 输出回填到 UNG CPU graph object 的耗时 |
| `recall` | 相对 exact filtered ground truth，不是相对 CPU 结果 |

端到端 recall 的定义：

```text
Recall@K = |UNG_search_result_topK ∩ exact_filtered_GT_topK| / K
```

其中 exact filtered ground truth 是：

```text
对 query labels 过滤后的候选点集合做 exact distance scan，得到真实 topK。
```

## 5. 方法细节

### 5.1 packed exact-anchor：中等 group 的稳定路径

packed exact-anchor 不是 naive strict topK。它的输入是 exact topK 候选，但输出图时加入 anchor / tail 设计，目标是保留导航性。

流程：

```text
1. 把多个中等 group 打包成连续 buffer。
2. 如果 group vectors 在内存中连续，直接 H2D，避免临时 host pack。
3. GPU 对每个点 exact scan 同组所有点，得到 topK 候选。
4. 输出边时保留 nearest head。
5. 剩余边位用 anchor tail / sampled tail 补充分散连接。
6. D2H 后保留 packed graph buffer，fill 阶段按 offset 直接写回。
```

为什么不是纯 topK：

```text
pure topK:          全部出边都是最近邻，容易局部化。
packed exact-anchor: 最近邻 head + 分散 anchor/tail，兼顾局部精度和导航性。
```

为什么更快：

| 优化点 | 作用 |
|---|---|
| 多 group packed batch | 减少每组单独 launch / malloc / copy |
| direct-H2D | group 已连续时不再重新 host pack |
| packed output buffer | D2H 后不再按 group scatter 再 fill |
| fill 线程控制 | 避免 CPU graph materialization 过度线程竞争 |

### 5.2 FastGrnndCuda：大 group 的近似候选 + 导航性修复

FastGrnndCuda 用 Tagore/GNN-Descent 产生候选，但不直接把原始候选图作为最终图。我们把它当作候选生成器：

```text
GNN-Descent candidates
  -> nearest head
  -> tail diversity
  -> reverse candidates
  -> degree repair
  -> final graph
```

几个关键设计：

| 设计 | 做什么 | 为什么提升 recall |
|---|---|---|
| nearest head | 保留最近的一批候选 | 保证局部近邻质量 |
| tail diversity | 从候选尾部等距采样少量边 | 避免图过度局部化 |
| reverse-tail | 加入“别人认为我近”的反向候选 | 补单向 GNN 漏边，改善连通性 |
| degree repair | 对低出度点补边 | 减少孤立点和弱连通分量 |
| local RNG-style prune | 用轻量 occlusion 保留多样边 | 接近 Vamana 的导航图思想，但比重 prune 便宜 |

### 5.3 相比 Tagore 为什么更好

一句话：**我们没有否定 Tagore 的 GPU GNN-Descent 候选生成，而是把 Tagore 不适合 UNG group workload 的后半段替换掉了。**

Tagore 原始路径可以粗略理解成：

```text
GPU GNN-Descent 生成候选
  -> GPU Vamana-style heavy prune
  -> 输出每个 group 的局部图
```

这个设计在“单个或少数大图”上是合理的，但在 UNG 里会遇到三个问题：

| Tagore 的问题 | 在 UNG group 场景里的表现 | 我们的改法 |
|---|---|---|
| heavy prune 太重 | 每个 group 都要做较复杂的候选筛选，many-group 下总成本很高 | 用 fixed-budget light/local prune，只处理有限候选 |
| 只靠 GNN 候选和 prune 不够稳定 | 轻 prune 会出现低出度、弱连通、单向漏边，搜索 recall 掉 | 加 reverse-tail、degree repair、tail diversity |
| 不区分 group size | 小 group 上 GPU launch/copy/fill 开销大，中等 group 用 GNN 又未必划算 | workload-aware router：小组 fallback，中组 packed exact-anchor，大组 FastGrnndCuda |
| 输出边界偏重 | GPU 结果还要回填到 CPU graph object，host pack / D2H / fill 变成瓶颈 | packed buffer、direct-H2D、减少 scatter/fill |

更具体地说，我们相比 Tagore 做了四类改变：

| 维度 | Tagore | 我们 |
|---|---|---|
| 候选生成 | GPU GNN-Descent | 大组保留 Tagore/GNN-Descent；中组直接 exact-anchor |
| 剪枝 | Vamana-style heavy prune，质量稳但慢 | fixed-budget local prune + reverse-tail + repair，质量/速度折中更适合 UNG |
| 分组调度 | 更接近统一 GPU 后端 | 按 `nx` 分流：small / medium / large 走不同路径 |
| 系统实现 | 更重的 per-group / output materialization | packed batch、direct-H2D、packed output、fast fill |

为什么 recall 更好：

```text
Tagore old:
  GNN 候选 -> prune 后主要保留局部近邻，轻 prune 时容易低出度/弱连通。

我们:
  nearest head 保留局部精度
  tail diversity 提供跨局部区域的跳转边
  reverse-tail 补“别人认为我近”的单向漏边
  degree repair 避免低出度点和孤立结构
```

为什么速度更快：

```text
Tagore 慢的主项不是 GNN 候选本身，而是重 prune 和外围物化。
我们把 prune 预算固定，把中等 group 改成 exact-anchor，把小 group fallback，
同时减少 host pack / D2H scatter / graph fill。
```

单组 `g1024_nx2048` 对 Tagore 的直接对比：

| 方法 | build_graph | prune/refine | L20 | L50 | L100 | L200 | L500 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 原始 Tagore | `9348.87 ms` | prune `4531.38 ms` | `0.9355` | `0.9765` | `0.9860` | `0.9915` | `0.9945` |
| FastGrnndCuda 旧版 | `3790.43 ms` | prune `657.63 ms` | `0.9375` | `0.9790` | `0.9870` | `0.9920` | `0.9955` |
| 最终 Reverse-augmented Local RNG | `4014.91 ms` | prune `810.08 ms` | `0.9515` | `0.9880` | `0.9930` | `0.9955` | `0.9965` |
| CPU Vamana | `9265.03 ms` | - | `0.9655` | `0.9910` | `0.9990` | `1.0000` | `1.0000` |

这个表说明两点：

```text
1. 相比原始 Tagore，最终版 build_graph 从 9348.87 ms 降到 4014.91 ms，约 2.33x。
2. 相比原始 Tagore，最终版 L20 从 0.9355 提到 0.9515，低 Lsearch 下导航性更好。
```

注意边界：

```text
我们不是声称所有场景都比 CPU Vamana recall 更高。
我们声称的是：相比 Tagore 原始后处理，我们在 UNG group workload 上用更轻的代价得到更适合 filtered search 的导航图。
```

### 5.4 bounded-complete：小 group 不盲目上 GPU

很多小 group 的计算量很小，GPU exact kernel 本身不慢，但外围成本很高：

```text
host pack + H2D + D2H + fill > actual compute
```

因此我们对小 group 采用 bounded-complete fallback：

```text
if nx <= max_degree + 1:
    每个点连同组所有其它点
else:
    每个点连 max_degree 条环形强连通边
```

这不是 Vamana 的逐边等价替代，但能显著减少大量小组的图物化成本。

## 6. 为什么我们的精度更高

先明确比较对象：我们不应该笼统说“精度高于 CPU Vamana”。CPU Vamana 仍是强质量 baseline。我们真正证明的是：

```text
相对原始 Tagore / naive strict topK / 过轻的 GPU prune，
我们的图在 UNG filtered search 中 recall 更高；
相对 CPU Vamana，我们在若干 workload 上做到 recall 接近或对齐，同时构建更快。
```

原因是 ANN graph search 需要的是 **可导航图**，不是每个点的 exact nearest-neighbor list。filtered search 从入口点出发，沿边扩展。如果边都集中在局部最近邻，图可能在局部团簇里很密，但跨团簇跳转能力差；如果 NN-Descent 候选有单向漏边或低出度点，搜索也容易漏掉正确区域。

因此我们的精度提升来自“导航性”而不是单纯最近邻精度：

| 问题 | Tagore / naive topK 的风险 | 我们的处理 |
|---|---|---|
| 只保留最近邻 | 图可能过局部，缺少跳转边 | anchor tail / sampled tail |
| NN-Descent 单向漏边 | 某些点入边少，弱连通分量变多 | reverse-tail candidates |
| light prune 过轻 | 低出度点、局部分裂 | degree repair |
| heavy prune 太慢 | 质量好但构建时间不可接受 | fixed-budget local prune |
| exact topK 不等于可导航图 | strict topK 历史上 UNG recall 明显差 | exact candidates + anchor/tail，不直接输出 pure topK |

可以把最终出边理解成三类边：

| 边类型 | 作用 | 对 recall 的影响 |
|---|---|---|
| nearest head | 保留最可靠的局部近邻 | 保证搜索进入正确区域后的局部收敛能力 |
| anchor / tail diversity | 保留少量分散边 | 提高跨局部团簇移动能力，避免 pure topK 过局部 |
| reverse / repair | 补“别人认为我近”的边和低出度点 | 改善弱连通、低入度/低出度、候选单向遗漏 |

单组 `g1024_nx2048` 方法质量表：

| 方法 | build_graph | prune/refine | L20 | L50 | L100 | L200 | L500 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 原始 Tagore | `9348.87 ms` | prune `4531.38 ms` | `0.9355` | `0.9765` | `0.9860` | `0.9915` | `0.9945` |
| FastGrnndCuda 旧版 | `3790.43 ms` | prune `657.63 ms` | `0.9375` | `0.9790` | `0.9870` | `0.9920` | `0.9955` |
| 最终 Reverse-augmented Local RNG | `4014.91 ms` | prune `810.08 ms` | `0.9515` | `0.9880` | `0.9930` | `0.9955` | `0.9965` |
| Method3 iter=4 | `8248.08 ms` | prune `4492` + refine `944 ms` | `0.9500` | `0.9880` | `0.9930` | `0.9965` | `0.9985` |
| CPU Vamana | `9265.03 ms` | - | `0.9655` | `0.9910` | `0.9990` | `1.0000` | `1.0000` |

解读：

- 相比原始 Tagore，最终版 L20 从 `0.9355` 提到 `0.9515`，build 从 `9348.87 ms` 降到 `4014.91 ms`。
- 相比 Method3 iter=4，最终版 recall 接近，但 build 从 `8248.08 ms` 降到 `4014.91 ms`。
- 相比 CPU Vamana，最终版仍有高 Lsearch recall 差距，但 build 约 `2.31x` 更快。

## 7. 为什么我们更快

速度提升来自两类：算法层面和系统层面。

对 reviewer 来说，最重要的是区分两种加速来源：

| 加速来源 | 具体含义 | 为什么不是“只因为 GPU 算力强” |
|---|---|---|
| 算法加速 | 用 fixed-budget light prune / reverse-tail 替代重 Vamana-style prune | 减少每个 candidate 和已接受邻居反复比较的开销 |
| 批处理加速 | 多 group packed batch，一次性处理很多小任务 | 避免每个 group 单独 launch/copy/malloc |
| 数据搬运加速 | direct-H2D、packed output、compact writeback | 旧路径大量时间花在 host pack、D2H 后 scatter、CPU fill |
| 图物化加速 | 控制 fill 线程和邻接表写回结构 | `std::vector` per-node 写边在 many-group 下会成为瓶颈 |

因此我们的速度优势通常不是来自某一个 kernel 的峰值 FLOPS，而是来自把构图流程改成：

```text
少做重 prune
+ 少做 host 临时打包
+ 少做小对象写回
+ 把足够多 group 合成 GPU 可并行的 batch
```

### 7.1 算法层面：避免重 prune

Amazon 1% x200 中，旧 heavy prune 的主要问题不是 GNN 候选生成，而是 prune 太重：

| Variant | direct build | H2D | GNN | prune | D2H | fill |
|---|---:|---:|---:|---:|---:|---:|
| old heavy prune | `26282 ms` | `1538.32` | `3551.54` | `19218.3` | `413.047` | `318.071` |
| top32 light prune | `5746.81 ms` | `1180.47` | `3198.35` | `712.392` | `134.631` | `247.246` |
| diversified light prune | `6365.69 ms` | `1448.82` | `3229.56` | `759.66` | `161.408` | `317.508` |

结论：

```text
old heavy prune 的 prune = 19218.3 ms
diversified light prune 的 prune = 759.66 ms
prune 本身约 25.3x 更快
```

同时 diversified light prune 的 L5000 recall 从 top32 的 `0.9029` 提到 `0.9056`，几乎不增加 prune 成本。

### 7.2 系统层面：减少 pack / D2H / fill 外围

packed exact-anchor 的旧性能瓶颈不是 GPU exact kernel，而是 host pack 和 CPU graph fill。direct-H2D + packed output 后：

| 路径 | Group graph | pack | GPU exact kernel | fill | L1000 recall |
|---|---:|---:|---:|---:|---:|
| 旧 exact path | `8999.26 ms` | `4140.61 ms` | `931.72 ms` | `2849.50 ms` | `0.867` |
| direct-H2D + fill16 | `3204.88 ms` | `0.04 ms` | `928.67 ms` | `1383.53 ms` | `0.867` |

结论：

```text
GPU exact kernel 基本没变，真正省掉的是 host pack 和 graph materialization。
```

## 9. 什么样的数据集上有效

我们的方法不是无条件替代 CPU Vamana。它的收益取决于 group size 分布，也就是每个 label group 里有多少点 `nx`，以及 group 数量是否足够多。

直观判断规则：

```text
nx 太小: GPU 计算量不够，外围开销盖过 kernel 收益
nx 中等: exact/anchor 可以快速构出质量稳定的图，是最甜点区
nx 很大: exact all-pairs 太贵，需要 GNN 候选 + reverse/repair 质量路径
group 数很多: batch 和 fallback 策略更重要，单组优化不够
```

更具体的适用表：

| 数据集结构 | 是否适合 | 原因 |
|---|---|---|
| 大量中等 group，例如 `nx≈128~512` | 很适合 | packed exact-anchor 能摊销 GPU，并保持质量 |
| 少量大 group，例如 `nx>=1024` | 适合，但要质量 route | FastGrnndCuda / reverse-tail 比 exact 更划算 |
| 大量小 group，例如 `nx<=64` | 不适合全 GPU | pack/H2D/D2H/fill 外围大于计算，应 fallback |
| many-group workload，例如 10%x40 | 适合 workload-aware router | 小组 fallback + 中组 exact + 大组 GNN 可以系统级加速 |
| 质量敏感的大 group，例如 x400 | 需要 reverse-tail/repair | 轻 prune 快但会掉 recall，需要多样性修复 |
| 100%x40 超大规模 | 当前是可扩展性结果，不是加速主结果 | 建图可完成，但 cross-edge pack_q 和查询 graph 随机访存成为新瓶颈 |

典型数据集规模：

| workload | points | groups | 主要压力 | 当前结论 |
|---|---:|---:|---|---|
| Amazon 1% x200 | `1,204,800` | `5,666` | `nx≈200` 中等组 | packed exact-anchor 最强 |
| Amazon 1% x400 | `2,409,600` | `5,666` | 大组质量/剪枝预算 | reverse-tail+repair 有效 |
| Amazon 10% x40 | `2,409,800` | `53,840` | many-group + 小/中组 | router 有 `1.53x` Index speedup |
| Amazon 100% x40 | `23,284,680` | `482,387` | 超大规模、显存、host pack、查询随机访存 | 可完成，但不是当前加速主结果 |

因此论文/展示里建议把有效范围说清楚：

```text
正结果：
  1% x200: 中等 group，packed exact-anchor 同 recall、group graph 2.22x。
  1% x400: 大 group，reverse-tail+repair 把 L5000 recall 拉回 CPU 同级。
  10% x40: many-group，workload-aware router 带来 1.53x index speedup。

边界结果：
  nx<=64: 不适合强行 GPU exact，应 fallback。
  100% x40: 建图可扩展，但查询 graph search 和 cross-edge 外围成为新瓶颈。
```

## 10. 跨组边 cross-edge 又做了什么优化

组内 PG 解决的是同一个 label group 内部的点怎么连边。跨组边解决的是：

```text
当查询入口落在某个父 group 或上层 group 时，
怎么给它补到子 group / 相关 group 的 point-to-point 边，
让搜索能从一个 group 走到另一个 group。
```

在构建阶段，cross-edge 可以抽象成大量 irregular group-pair topK 问题：

```text
for each connected group pair (source group, target group):
    对 source group 中的点作为 query
    在 target group 的点里找 topK neighbor
    把这些边加入全局图
```

难点不是单个 GEMM，而是这个 workload 非常碎：

| 难点 | 表现 |
|---|---|
| `(nq, nx)` 极不规则 | 有的 group pair 很小，有的很大，单独调用 GPU library 会被 API/launch/pack 开销吃掉 |
| 同一个 query group 会连接多个 target group | 需要跨 target 合并 topK，否则会产生重复候选或 host merge 开销 |
| full-quality 还有 `additional_edges` | 不能只测 skip-additional kernel，否则 recall 口径不完整 |
| 输出要写回 CPU graph | `SearchQueue`、per-node vector、D2H scatter 和 merge 会成为 Amdahl 瓶颈 |

### 10.1 我们的 cross-edge 方法

最终保留的主线是 **target-centric fused topK + double-buffer + flat/universal route**。可以理解成：

```text
1. 不再每个 group pair 单独调用一次 CPU/GPU topK。
2. 把很多 group pair 合成 descriptor batch。
3. GPU kernel 内完成 distance + topK，尽量少把中间距离矩阵写回。
4. 用 double-buffer 让 H2D / kernel / D2H 分块流水。
5. 对支持的 target group 走 fast path；极端大组或不支持形态 fallback。
6. flat-id / universal route 减少 SearchQueue 和 host 小对象写回。
```

几个实现分支的边界：

| 分支 | 作用 | 当前结论 |
|---|---|---|
| grouped fused topK | 把 distance 计算和 topK 合在一个 GPU 路径里 | 是最稳定的 cross-edge 加速来源 |
| direct-qid double-buffer | 分块流水，减少每批同步和写回 | 10%x40 上 full-quality 有效 |
| partial split routing | 避免少数大组让整批 all-or-nothing fallback | x200 上 cross `3900.81 -> 2657.23 ms` |
| universal flat double-buffer | target-centric + double-buffer + GPU global merge + flat-id output | x200 full-quality 当前最强 cross-edge 路线 |
| source-centric WMMA | 按 source group 聚合，理论上减少 qid merge | 方向有价值，但当前单阶段实现不是主结果 |
| qid-lock global merge | 在 GPU 上用 per-qid lock 合并 | 负结果，atomic/lock contention 让 kernel 变慢 |

### 10.2 加速效果

#### x100 公平 baseline：说明不是只打赢弱 CPU Vamana

Amazon 1% x100 的 cross-edge baseline 对比：

| 方法 | Cross ms | 相对 final fused |
|---|---:|---:|
| CPU Vamana cross | `18735.8` | `22.07x` slower |
| CPU exact scan, 128 threads | `2389.8` | `2.82x` slower |
| cuVS per-group brute force | `3730.5` | `4.39x` slower |
| SGEMM + topK | `1395.9` | `1.64x` slower |
| final fused | `848.9` | `1.00x` |

这个表的意义是：我们的 cross-edge 不是只比原始 CPU Vamana 快，也比“CPU 并行暴力”“逐组调用 cuVS”“SGEMM 后再 topK”这些更强 baseline 快。原因主要是：

```text
把很多小的 group topK 合并成批处理，
并减少 group API 调用、距离矩阵中间物化、D2H 和 host merge。
```

#### x200 full-quality：universal flat double-buffer 的正结果

Amazon 1% x200，固定 CPU Vamana group graph 和 CPU Vamana `additional_edges`，只替换 cross-edge：

| 路径 | Cross ms | generate | additional_edges | GPU kernel cumulative | D2H | merge_cross | L1000/L5000 recall |
|---|---:|---:|---:|---:|---:|---:|---:|
| partial DB target route | `2657.23` | - | - | - | - | - | `0.866 / 0.907` |
| universal flat all-DB | `2494.21` | `1636.2` | `843.5` | `1887.5` | `1.2` | `0.7` | `0.871 / 0.911` |

这个结果说明 universal route 可以接上 full-quality `additional_edges` 和 search recall，不只是 skip-additional smoke test。它比已有 partial double-buffer 还略快，且 recall 没有崩。

#### x200 partial split：调度边界本身就能带来 1.47x

早期 direct-qid double-buffer 是 all-or-nothing：一批里只要混入少数超大 target group，整批就回退旧路径。partial split 后：

```text
supported target groups: 5173
fallback target groups: 22
```

| 路径 | Cross ms | kernel ms | 说明 |
|---|---:|---:|---|
| target-current before split | `3900.81` | `2095.8` | 少数大组拖累整批 |
| naive no-split all-or-nothing | `4332.46` | `2569.0` | 负结果 |
| partial split routing | `2657.23` | `1636.0` | 只让 22 个大组 fallback |

结论：

```text
Cross speedup = 3900.81 / 2657.23 = 1.47x
Kernel speedup = 2095.8 / 1636.0 = 1.28x
```

这说明 cross-edge 慢的一个核心原因是 **调度边界不合理**，不是 fused kernel 本体完全不够快。

#### 10%x40：many-group full-quality 端到端构建有效

10%x40 有 `53,840` 个 group，是典型 many-group workload。历史 full-quality 点：

| 方法 | Index ms | Group ms | Cross ms | L100 | L500 | L1000 |
|---|---:|---:|---:|---:|---:|---:|
| CPU Vamana group + GPU direct-qid cross + CPU additional_edges | `36053.3` | `18218.5` | `9777.3` | `0.8647` | `0.8980` | `0.9080` |
| FastGrnndCuda + complete fallback + GPU direct-qid cross + CPU additional_edges | `23497.4` | `5147.2` | `9451.1` | `0.8668` | `0.8980` | `0.9103` |

这张表里 cross-edge 本身从 `9777.3` 到 `9451.1` 不是最大变化，最大收益来自 group graph；但它说明 cross-edge GPU path 可以在 many-group full-quality 下保持 recall，并成为系统组合的一部分。

### 10.3 为什么 cross-edge 更快

和组内图类似，cross-edge 的速度优势也不是单纯“GPU FLOPS 更高”，而是减少了整个 pipeline 的无效工作：

| 优化 | 省掉什么 |
|---|---|
| fused distance + topK | 不写完整距离矩阵，不做独立 topK pass |
| grouped descriptor batch | 不按 group pair 逐个调用 cuVS / cuBLAS / CPU scan |
| double-buffer | H2D、kernel、D2H 分块流水，减少同步等待 |
| partial split | 小/中 group 继续走 fast path，少数大 group 才 fallback |
| flat-id / universal route | 减少 `SearchQueue`、D2H scatter、host 小对象 merge |
| delayed GPU cache release | 避免把 cuda free / unregister 同步放回 cross-edge 关键路径 |

一个重要发现是：在 full-quality 下，`additional_edges` 可能比 GPU kernel 还贵。例如 Amazon 1% x100 smoke 中：

```text
CPU Vamana additional_edges_ms = 1269.257 ms
GPU kernel event             = 655.969 ms
```

所以后续大幅加速不能只继续调 fused topK kernel，还要把 `additional_edges` 和 graph 输出边界一起改成 flat/CSR 或 GPU-native 后端。

### 10.4 cross-edge 适合什么数据集

| 数据集结构 | 是否适合 cross-edge GPU | 原因 |
|---|---|---|
| group pair 很多、每个 pair 中等大小 | 很适合 | 能把大量 irregular topK 合成批处理，摊销 launch/API/pack |
| `nq * nx` 足够大但单组不至于爆显存 | 很适合 | GPU kernel 有足够计算量，double-buffer 能隐藏搬运 |
| many-group workload，例如 10%x40 | 适合 | cross-edge GPU 能作为 full-quality 系统路径稳定工作 |
| x100/x200 repeat workload | 适合 | x100 有强 baseline 加速，x200 有 universal full-quality 正结果 |
| 很小 group pair 占绝大多数 | 不适合全 GPU | API/pack/D2H/merge 可能大于计算，需要 batching 或 CPU fallback |
| 少数超大 target group 混在 batch 中 | 需要 partial split | 否则 all-or-nothing fallback 会拖慢整批 |
| 100%x40 超大规模 | 目前是可完成但不适合作为加速主结果 | X-streaming 解决显存边界，但 `pack_q=450338.9 ms` 成为主瓶颈 |
| 需要 CPU Vamana `additional_edges` full-quality | 能跑，但加速受限 | additional_edges 和 CPU graph 输出可能成为新瓶颈 |

### 10.5 100%x40 的边界结果

100%x40 有 `23,284,680` 点、`482,387` groups。resident GPU cross-edge 曾因需要约 `71.5GB` 的 `g_d_all_X` 而 OOM；X-side streaming 后可以完成 strict skip-additional build：

| 阶段 | 时间 ms | 说明 |
|---|---:|---|
| Index | `945683` | 可完成，但不作为加速主结果 |
| cross-edge generate | `697114.7` | X-streaming exact cross-edge |
| pack_q | `450338.9` | Q 侧重复 host 展开成为主瓶颈 |
| GPU kernel | `72749.8` | kernel 不是最大项 |

结论：

```text
100%x40 证明了可扩展性边界已经推进，
但 X-streaming v1 不是性能优化结果。
下一步必须减少 Q 侧重复 pack，例如 Q-side device cache/gather、
source-centric two-stage、或者 flat/CSR 输出边界。
```

## 11. 统一最优 router 的阶段加速比和耗时占比

这一节只回答一个问题：**如果统一使用当前推荐的 workload-aware router，各数据集上端到端、组内图、跨组边分别是什么表现？**

这里不把不同实验里的“单阶段最优”硬拼成一个未实测组合。表里的 `After` 都是已经跑过的组合；如果某个 cross-edge 最优只来自 skip-additional 或 diagnostic，会单独放在后面的专项表。

当前推荐 router 的含义：

```text
build-time static routing by group size:
  small group  -> CPU / bounded fallback
  medium group -> packed exact-anchor
  large group  -> FastGrnndCuda + reverse-tail / repair

cross-edge:
  fused / direct-qid / universal flat route where that full-quality run has been measured
```

字段含义：

| 字段 | 含义 |
|---|---|
| `Before` | 对应该数据集的可比 baseline，一般是 CPU Vamana group + 已有 cross-edge 路径 |
| `After` | 当前推荐 router 在该数据集上的实测组合 |
| `占比` | 该阶段耗时占同一行 `Index total` 的比例 |
| `阶段加速比` | `Before ms / After ms` |
| `贡献占总节省` | `(Before stage - After stage) / (Before Index - After Index)`；负数表示该阶段变慢，超过 `100%` 表示其它阶段回退抵消了部分收益 |

| 阶段 | Before ms / 占比 | After ms / 占比 | 阶段加速比 | 贡献占总节省 |

## 12. 查询入口组 scan 加速

前面的 group graph 和 cross-edge 都是 **建图阶段**。查询阶段还有一个单独瓶颈：给定 query labels，需要先找到一批入口 groups，然后后续图搜索才会从这些 groups 的 entry points 开始。

原始 CPU 路径对应 `get_min_super_sets_debug()`，可以粗略拆成：

```text
1. scan 所有 group labels，找出满足 query_labels subset labels(group) 的候选 C
2. 在 C 上做 minimal / superset 剪枝，尽量只保留最上层入口 groups
3. 输出 CPU-side group ids，供后续 get_entry_points_given_group_id() 和 iterate_to_fixed_point()
```

这一步在 many-group workload 上很贵。GPU 优化不是要求和 CPU exact minimal 输出完全一样，而是采用 **correct-cover** 语义：

```text
必须覆盖所有真正满足 query labels 的 group；
允许输出少量冗余入口 group；
冗余入口不会漏召回，但可能增加后续 graph search 工作量。
```

### 12.1 GPU correct-cover 算法

对每个 query：

```text
C = {g | query_labels subset labels(g)}
F_raw = {g in C | |query_labels| <= |labels(g)| <= |query_labels| + delta}
F = first_cap(F_raw)
Covered = union(descendants(f) for f in F)
Uncovered = C - Covered
Output = F union Uncovered
```

变量含义：

| 变量 | 含义 |
|---|---|
| `C` | 所有满足过滤条件的候选 groups |
| `delta` | frontier 的 label-size 窗口；越大越可能找到更少的上层入口，但 coverage OR 更贵 |
| `cap` | 每个 query 最多拿多少个 `F_raw` 里的 frontier groups 做 descendant coverage OR |
| `Covered` | 被已选 frontier 的后代覆盖的候选 groups |
| `Uncovered` | 没被覆盖的候选 groups，必须直接输出以保证不漏 |
| `avg_frontier_groups` | 平均每个 query 参与 coverage OR 的 frontier groups 数 |
| `avg output groups` | 平均最终输出入口 groups 数 |

为什么能保证覆盖：

```text
对任意 g in C：
  如果 g 被某个 f in F 的 descendants 覆盖，则从 f 进入可以覆盖到 g；
  如果没有被覆盖，则 g 会进入 Uncovered 并直接输出。

所以 Output = F union Uncovered 不会漏掉任何 C 中的 group。
```

`cap` 截断不会破坏正确性。它只会减少 `Covered`，让更多 group 落入 `Uncovered`，结果是输出更冗余，但仍然覆盖正确。

### 12.2 实现细节

GPU benchmark 工具是 `UNG/codes/tools/query_entry_group_bench.cu`，脚本入口是 `scripts/benchmarks/run_query_entry_group_bench.sh`。最终保留的 provider 是 `gpu_cover_frontier`，旧的只取 frontier 的 `gpu_frontier` 因为不能保证 coverage，已经不作为有效实现考虑。

实现上使用 dense bitset 批处理多个 query：

| 步骤 | 做什么 |
|---|---|
| candidate bitset | 对每个 query 并行测试 `query_labels subset labels(group)`，得到 `C` |
| frontier compact | 把满足 `delta` 窗口的 frontier groups compact 成连续 id list |
| list-driven coverage OR | 只遍历 compact 后的 frontier id，对 descendant bitset 做 OR |
| output select | 输出 `selected_frontier_bits | (candidate_bits & ~covered_bits)` |
| CPU materialize | 当前完整 bitset D2H 后，在 CPU 侧物化输出统计 |

关键优化是 **list-driven coverage**。旧写法会对每个 `(query, bitset word)` 扫完整 frontier bitset；新写法先 compact frontier ids，再只对这些 ids 的 descendant bitset 做 OR。100%x40、`delta=1` 上，内部路径从约 `762.92 ms` 降到约 `60.72 ms`，约 `12.2x`。

### 12.5 scan 加速的展示边界

对外可以这样说：

```text
我们把查询入口组选择从 CPU exact-minimal 改成 GPU correct-cover 批处理。
它保证不漏任何满足过滤条件的 group，但允许冗余入口。
在 Amazon 100%x40、nq=10240 上，入口组阶段相对 CPU scan 128T 达到 19.85x。
```

不能这样说：

```text
端到端 UNG 查询已经 19.85x 加速。
```

原因是：

| 限制 | 说明 |
|---|---|
| 尚未接入正式 search path | 当前是独立 benchmark，正式 `search_UNG_index` 仍调用 CPU `get_min_super_sets_debug()` |
| 输出不是 exact minimal | GPU 输出 groups 多于 CPU exact minimal，可能增加后续 entry point materialization 和 graph search |
| D2H 仍可优化 | 现在回传完整 bitset，100%x40、`nq=10240` 约 `25 ms`；生产路径应输出 compact `(offsets, group_ids)` |

## 13. 最终展示口径

我们应该避免这样说：

```text
我们用 GPU exact topK 替代了 Vamana。
```

更准确的说法是：

```text
我们提出了一个面向 UNG 构建的 workload-aware GPU backend。
组内 PG 不直接输出 strict topK 图，而是根据 group size 选择 bounded fallback、packed exact-anchor 或 FastGrnndCuda。
跨组边则把大量 irregular group-pair topK 合成 fused / double-buffer / flat-output 的批处理路径。
查询入口组选择则用 GPU correct-cover 批处理替代高成本 CPU scan/minimal 阶段。
组内图通过 anchor/tail/reverse/repair 恢复导航性，跨组边通过 fused topK、partial split 和 flat/universal route 降低 prepare、D2H 和 host merge 开销，查询入口通过 bitset/frontier/descendant OR 保证 coverage。
在 Amazon 1% x100/x200、1% x400、10% x40、100%x40 上，它分别验证了 cross-edge 加速、中等组、大组、many-group、查询入口 scan 和超大规模边界。
```

一句话总结：

> 我们的贡献不是“GPU 算 topK 更快”，而是把 GPU 候选生成、导航性修复、跨组 fused topK、查询入口 correct-cover scan 和 workload-aware routing 合成一个适合 UNG filtered search 的系统。
