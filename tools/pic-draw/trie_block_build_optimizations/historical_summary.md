# Trie block 构建优化结果汇总

四组绘图使用旧版构建器的完整八数据集矩阵；删除辅助预计算后的新版，仅第四组完成八数据集重测。
**两套数据分开保存，不能拿新版第四组替换旧版第四组，与旧版前三组计算优化加速比。**

## 数据和口径

- CPU：块内 CPU Vamana；GPU：GNN-Descent＋FastGrnnd，单 stream、关闭优化 topK。
- GPU+LB：4 stream 按块负载均衡，关闭优化 topK；GPU+LB+TopK：同时启用两项优化。
- topK 指第 K 距离阈值过滤、局部 Bitonic 排序和二分排名并行归并；所有 GPU 组保留 FastGrnnd 剪枝。
- 各样本重建基础 Trie。主指标是进程端到端墙钟，包含基础与块两阶段的加载、构建、保存；排除编译、锁等待、校验、汇总与清理。
- 块内图时间单列；块间统一 CPU 搜索。块内计时收益不能直接作为整个索引加速比。
- 单层 500:trie，出度 32，跨块边数 4，Lbuild=100，alpha=1.2，60 个 CPU 线程；GPU K 请求 128（编译上限 96）、M=64、迭代 4、批次点数上限 65536。
- 七数据集旧第四组的 case 目录已不存在，相关值来自保留的 all_runs.csv 和 comparison.csv，并已逐项核对；manifest 中保留原配置哈希。其余 case 配置及 meta 可继续复核，详情见 audit_status。
- 历史矩阵的构建器 SHA256 全部一致。Amazon 来自两个独立会话：GPU 为 3 次测量的中位数，其他方法各 1 次；预热排除。其他七数据集每组仅 1 次。
- Amazon 历史批次未开启块间边预分配，其他七数据集开启；同一数据集内部各方法一致。新版八数据集均开启预分配。
- 时间结果尚不能证明各近似图的搜索召回率相同，单次样本也不能证明稳定的微小加速。

## 如何解读优化收益

1. CPU→GPU 是主要收益来源。八数据集真实端到端加速为 1.74–5.75 倍。
2. 同时启用两项优化，相对无两项优化的 GPU，八数据集块内构图加速为 1.14–1.43 倍。
3. 七数据集同批消融中，负载均衡基础上再加 topK，块内耗时全部下降，降幅 10.9%–33.0%。负载均衡单独在 Tiktok 上有退化，不能称为普遍稳定收益。
4. 端到端收益小于块内收益：组合相对仅负载均衡，在 VImg、Music、Laion 的历史端到端时间反而增加。阶段归因表明主要差额来自独立重建的公共基础 Trie；不能解释为两项 GPU 优化互相拖慢。
5. 新版删除了固定图搜索未用的全量后代、覆盖集合、属性二分图及选择器特征。新版第四组变快包含这些公共代码清理收益，不能归入 LB/topK 消融。

## 文件与重新生成

- `historical_four_methods.csv`：32 行长表，秒；含各阶段中位数、最小值、最大值、样本数及逐样本来源。
- `historical_four_methods_wide.csv`：8 行宽表，每种方法各一列时间，便于 Excel、Origin 等绘图。
- `historical_speedups.csv`：CPU→GPU、GPU→LB、LB→LB+TopK 等加速倍数和耗时降幅；正降幅为变快。
- `graph_only_latest.csv`：新版第四组 8 行，独立保存，不混入四组主图。
- `source_manifest.json`：原始 CSV、manifest 及可用配置/meta 的 SHA256，缺失文件标为 null；保留构建器版本与原配置记录哈希。
